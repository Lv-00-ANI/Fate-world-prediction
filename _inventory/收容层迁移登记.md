## 一、迁移判据（三条，缺一不可）

一个 `Legacy` 模块能迁入 `FateV2`，必须同时满足：

| # | 判据 | 为什么 |
|---|---|---|
| **1** | **零 Legacy 依赖**（只 import Mathlib，或零 import） | 否则迁一个会拖进整条依赖链，失去「逐步迁移」的意义 |
| **2** | **编译通过** | 见 §三 的验证流程 |
| **3** | **有定理**（theorem / lemma 数 > 0） | 排除纯注释 / 纯接口文件 |

### 评估结果（实测）

| 项 | 数字 |
|---|---:|
| `Legacy` 模块总数 | 851 |
| **零 Legacy 依赖且有定理** | **56** |
| 其中与 `FateV2` 重名（已迁过） | 14 |
| **实际待迁** | **42** |

**评估脚本**：`_migration/assess.py`
**完整数据**：`_inventory/迁移候选.csv`

> **重名的那 14 个不是待迁对象。** 抽查 `CausDAG` / `ObsEstimationStrong` /
> `ErrorCriterion` / `AttrAcceptable`，Legacy 版与 FateV2 版的**定理数完全相同**——
> 说明 FateV2 版就是已迁移的适配版，只是命名空间和 import 不同。

## 二、迁移动作定义

| 动作 | 含义 | 本批采用 |
|---|---|---|
| **A 原样** | 代码可直接用，一字不改 | 未用 |
| **B 适配** | 需改命名空间 / import | ✅ **全部采用** |
| **C 重写** | 旧实现与裁决冲突，需新写 | 未用 |
| **D 弃用** | 已被证伪，只留档 | 未用 |

### 实际改动（仅两处）

1. **改命名空间**：
   - `namespace Fate` → `namespace FateV2.<Domain>`
   - `end Fate` → `end FateV2.<Domain>`
   - 复合形式 `namespace Fate.Sub` → `namespace FateV2.<Domain>.Sub`
   - 裸命名空间 `namespace Lattice` → `namespace FateV2.<Domain>.Lattice`
2. **加迁移登记头**（插在第一个 `/-!` 之前）

**定义、定理、证明体逐字保留。** 这是本批迁移的硬纪律。

## 三、验证流程

```
① 判据筛选（assess.py）
   ↓
② 迁移（port.py --one / --batch）
   ↓
③ 编译验证      lake build FateWorld.FateV2.<Domain>.<Name>
   ↓ 失败 → 删除已写文件，回滚，记录原因
④ 公理审计      #print axioms（逐定理）
   ↓ 出现 sorryAx → 标记不合格
⑤ 登记本文件
```

**回滚保证**：`port.py` 在编译失败时会**删除已写入的目标文件**，
不会留下半个模块。

## 七、这批迁移不做什么

| 不做 | 原因 |
|---|---|
| **不动有 Legacy 依赖的模块** | 它们会拖进依赖链。需先迁依赖，再迁自身——属后续批次 |
| **不改证明体** | 只改命名空间。任何改动都会让「迁移」变成「重写」 |
| **不声称迁入即正确** | 迁移只保证**可编译**。定理正确性需逐条验证 |
| **不迁 129 个重名模块** | 它们已在 FateV2 中有对应版本 |
| **不删 Legacy 原件** | 收容层保留原文件，供对照 |

## 十一、第 1 层迁移的完整规则（本轮突破）

第 1 层迁移失败率一度很高。**根因不是「依赖没迁」，而是「open 语句没改写」。**

### 问题

Legacy 里有 **823 处裸 `open`**，例如：

```lean
open PearlHierarchy SCMSemantics Finset
open Causalean.Graph
```

这些名字在 Legacy 里是 `Fate.PearlHierarchy` / `Causalean.Graph`。
迁到 FateV2 后它们变成 `FateV2.Modeling.PearlHierarchy` / `FateV2.Modeling.Graph`，
裸 `open` 就失效了。

**实测**：`CfNecessity` 只做 import + namespace 改写会报
`unknown namespace PearlHierarchy`；补上 open 改写后编译通过。

### 三条改写规则（缺一不可）

| # | 规则 | 示例 |
|---|---|---|
| 1 | **import 重定向** | `import FateWorld.Legacy.X` → `import FateWorld.FateV2.<域>.X` |
| 2 | **命名空间改写** | `namespace Fate` → `namespace FateV2.<域>` |
| 3 | **open 改写** ⭐ | `open PearlHierarchy` → `open FateV2.Modeling.PearlHierarchy` |

### ⚠ open 改写的两个陷阱

**陷阱 1：section 名不能改。**
`open SCM` 里的 `SCM` 可能是 `section SCM` 的名字，不是命名空间。
误改会报 `unknown namespace`。⟹ **只改写映射表里查得到的目标**。

**陷阱 2：Mathlib 命名空间不能改。**
`Finset` / `Set` / `Filter` / `Topology` / `MeasureTheory` 等必须保持原样。

### 支撑工具（本轮新建）

| 脚本 | 作用 |
|---|---|
| `_migration/nsscan.py` | 扫描硬编码 `Fate.*` 引用，输出 `_inventory/硬编码命名空间.csv` |
| `_migration/nsmap.py` | 建立 Legacy ns → FateV2 ns 映射表（183 条） |
| `_migration/port_v2.py` | 三重规则迁移器 |
| `_migration/batch_v2.py` | 批量迁移 + 自动判域 |

### 验证

| 模块 | 定理 | 结果 |
|---|---:|---|
| `ResidualReduces` | 58 | ✅（v1 也能过） |
| `T43Abduction` | 56 | ✅（需 open 改写） |

## 十二、五条迁移规则（最终版，全部经实测验证）

第 1 层迁移经历了 5 轮失败，每轮暴露一条缺失规则。最终版如下：

| # | 规则 | 触发它的实测反例 |
|---|---|---|
| 1 | **import 重定向**<br>`FateWorld.Legacy.X` → `FateWorld.FateV2.<域>.X` | 所有第 1 层模块 |
| 2 | **命名空间全文替换**<br>`Fate.*` → `FateV2.<域>.*`（**不能只改第一处**） | `InterventionTight` 残留 `namespace Fate.WorldScenario.Tight` |
| 3 | **open 改写**<br>`open PearlHierarchy` → `open FateV2.Modeling.PearlHierarchy` | `CfNecessity`：`unknown namespace PearlHierarchy` |
| 4 | **open 依赖所在的域**<br>依赖在别的域 → `open FateV2.<依赖域>` | `TwoVersions`：`Unknown identifier WiringConvergence.stepMap` |
| 5 | **open 同域的兄弟命名空间**<br>依赖在同域 → `open <真实子命名空间>` | `InterventionTight`：`Unknown identifier InterventionSelection.Good` |

### 规则 5 的关键陷阱

**不能用模块名当命名空间名。**

实测：`PolicyAlgorithm.lean` 里的 namespace 其实叫 `WorldScenario`。
按模块名 open `PolicyAlgorithm` 会报 `unknown namespace`。
⟹ 必须**打开依赖模块文件，读出真实的 namespace**。

### 为什么 Legacy 不需要这些

Legacy 里多数模块共享 `namespace Fate` 这一层：

```
Fate
├── WiringConvergence      ← WiringConvergence.lean
├── TwoVersions            ← TwoVersions.lean（能直接写 WiringConvergence.stepMap）
└── InterventionSelection  ← 同理
```

**因为都在 `Fate` 下，兄弟模块互相可见，无需 open。**

FateV2 按域切分后（`FateV2.Loop` / `FateV2.Predict` / …），
这种隐含可见性丢失 ⟹ 规则 4、5 就是在**显式重建这份可见性**。

### 规则 2 的陷阱

有的文件里有**多处** namespace 写法：

```lean
namespace Fate                          -- 顶层
...
namespace Fate.WorldScenario.Tight      -- 后面又开一个复合的
```

只改第一处会留下第二处未改，引用解析不到。必须全文替换。
