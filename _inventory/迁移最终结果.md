## 二、唯一的失败：`Stage2/G2Backdoor.lean`

### 现象

34 条错误，全部集中在同一个文件：

```
error: FateWorld/Legacy/Stage2/G2Backdoor.lean:150:14: Unknown identifier `Fate.R290.SetupWithM`
error: FateWorld/Legacy/Stage2/G2Backdoor.lean:165:6:  Unknown identifier `Fate.R290.IsDescendantM`
error: FateWorld/Legacy/Stage2/G2Backdoor.lean:226:4:  Unknown identifier `Fate.R290.Demo.demo.fM`
...（共 30 处 Fate.R290 引用）
```

### 根因：原作者的命名空间写错了

实测全库：

| 检查 | 结果 |
|---|---|
| `namespace Fate.R290` 出现次数 | **0** |
| `namespace Fate.R289` 出现次数 | **1**（`BackdoorWithM.lean:181`） |
| `G2Backdoor.lean` 中 `R290` 引用数 | **30 处** |
| 全库其他文件引用 `R290` | **0 处**（只有这一个文件） |

**⟹ `BackdoorWithM.lean` 定义的是 `Fate.R289`，而 `G2Backdoor.lean` 通篇按 `Fate.R290` 引用。**
这是**源文件固有不一致**，与迁移无关。

### 为什么迁移没有引入它

迁移只改了一处：

```
源:  import Fate.BackdoorWithM        →  新:  import FateWorld.Legacy.BackdoorWithM
```

其余 100% 逐字相同（已比对）。**命名空间 `Fate.R290` 原样保留自源文件。**

### 处置（按迁移纪律，本阶段不改代码）

按 `迁移规则.md` 纪律 1「不改代码」，**未修复**，只在 `_inventory/待修缺陷.csv` 登记。

若要修复，只需把该文件里 30 处 `Fate.R290` 改为 `Fate.R289`。但这属于**修改历史代码**，
应按升层流程单独做并留证据，不在迁移阶段顺手改。

## 三、迁移过程的关键发现（方法论）

### 3.1 为什么前四次都失败

| 尝试 | 失败模式 |
|---|---|
| 1–3 | `lake build` 一把梭 → 长时间无输出 → 分不清「在编译」还是「卡死」→ 中断重来 |
| 4 | 用 Job 句柄判断状态 → Job 随会话销毁后消失，但子进程变成孤儿继续跑 |

**根因**：`lake build` 的进度**不是**从 Job 状态可读的。

### 3.2 有效的观察方式

| 无效 | 有效 |
|---|---|
| 看 Job 状态 | **数 `.olean` 文件个数**（单调递增，不会骗人） |
| 看「有没有输出」 | 看 `Get-Process lean` 的 **CPU 是否增长** |
| 看「改了 N 个文件」 | 统计**改写了多少处 import**（才能发现漏网） |

### 3.3 三个真实踩过的坑

1. **素材边界 ≠ `Fate/` 边界** —— 顶层还有 9 个文件被无前缀引用
2. **Lean 新版 `module` 语法** —— `import` 不在行首（`module` / `public` 修饰），
   `^import` 正则会漏掉 10 处，直到构建才暴露
3. **并发撞 Mathlib olean 锁** —— 需 `LEAN_NUM_THREADS=1`
