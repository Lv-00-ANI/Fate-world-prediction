### 三个只有实际构建才会暴露的问题

**① 素材夹顶层还有 9 个 `.lean`，第一次迁移漏掉了。**

`Fate/` 子目录之外，素材夹顶层还躺着 9 个独立模块：

| 文件 | 行数 | 作用 |
|---|---:|---|
| `CausDAG.lean` | 399 | 因果 DAG 基础 |
| `CausSeparation.lean` | 772 | 因果分离 |
| `CausBayesBall.lean` | 374 | Bayes-Ball |
| `CausBayesBallEquiv.lean` | 123 | Bayes-Ball 等价性 |
| `CausActivePath.lean` | 673 | 活跃路径 |
| `RealFCA.lean` | 224 | 实数版 FCA |
| `RealTemporalLayer.lean` | 406 | 实数版时序层 |
| `RealUpDown.lean` | 203 | 实数版上下确界 |
| `Fate.lean` | 853 | **旧总入口**（import 了近 700 个模块） |

它们被 `Fate/` 下的模块以**无前缀**方式引用（`import CausDAG`），
所以只迁 `Fate/` 会导致 `unknown module prefix 'CausDAG'`。
**已补迁到 `Legacy/_root/`。**

**⟹ 教训：只看一个目录会漏。素材的边界不等于 `Fate/` 的边界。**

**② 这个代码库用的是 Lean 新版 `module` 语法，`^import` 正则抓不到。**

这是最有欺骗性的一条。文件形如：

```lean
module
public import CausBayesBall
```

`import` **不在行首**，前面有 `module` / `public` 修饰。
用 `^\s*import` 匹配会漏掉，用 `^import` 更是完全匹配不到。

**后果**：改写脚本报了「已改写 1,788 处」，看起来成功，
但**实际上有 10 处漏网**，直到 `lake build` 才暴露为
`unknown module prefix 'CausDAG'`。

**正确正则**：

```python
r'(?m)^\s*(?:(?:module|public|private|meta)\s+)*import\s+(\S+)'
```

**复核结果**：851 个文件、2,728 处 `FateWorld.Legacy.*` + 1,031 处 `Mathlib.*` + 1 处 `Batteries.Data.Rat`，**0 处漏网**。

**⟹ 教训：改写脚本必须先统计「改写前后 import 总数」，不能只看「改了几个文件」。**

**③ 并发构建会撞 Mathlib 的 `.olean.private` 文件锁。**

```
error: failed to read file 'Mathlib/Data/Seq/Basic.olean.private'
error: failed to read file 'Mathlib/CategoryTheory/Sites/Coverage.olean.private'
```

文件**存在且完好**（1.6 MB），这是并发读同一 `.olean.private` 的句柄竞争。

**规避**：`$env:LEAN_NUM_THREADS='1'` 后再 `lake build`。

## 二、与 `命运-v2` 的模块关系

| 项 | 数字 |
|---|---:|
| `命运-v2/FateV2` 模块 | 254 |
| `Legacy` 模块 | 842 |
| **两边同名** | **125** |
| **只在 Legacy** | **717** |
| 只在 `命运-v2` | 128 |

### 关键结论

**`Legacy` 比 `命运-v2` 多出 717 个模块。** 这些就是上游从未纳入工程的代码。

「只在 `命运-v2`」的 128 个是新写的（`Core/` 构造性核、`Bridge/` 账本桥、
`Demo/` 可执行演示、`Data/` 数据接入等），**在素材夹里没有对应源文件**。

### 两边同名的 125 个怎么理解

**不是同一份代码。** `命运-v2` 里那 125 个是**迁移时的适配版**（改了命名空间、去掉 `ℝ`/`Measure` 依赖等），
而 `Legacy` 里的是**原始版**。

⟹ **这两套可以互为对照**：若怀疑 `命运-v2` 某处适配时改错了，可回到 `Legacy` 看原文。
完整对照表见 [`同名模块对照.md`](同名模块对照.md)。

## 三、目录结构

```
FateWorld/
├── Legacy/
│   ├── Concrete/          ← 源: Fate/Concrete/       (1 个)
│   ├── Stage0/            ← 源: Fate/Stage0/         (4 个)
│   ├── Stage2/            ← 源: Fate/Stage2/         (35 个)
│   └── *.lean             ← 源: Fate/*.lean          (802 个)
└── FateWorld.lean         ← 自动生成的汇总入口（import 全部 842 个）
```

**命名空间**：`FateWorld.Legacy.<原模块名>`

> ⚠ **注意**：文件内的 `namespace Fate.XXX` 声明**保持原样未改**。
> 这意味着命名空间与模块路径不一致（模块路径是 `FateWorld.Legacy.X`，
> 内部命名空间是 `Fate.X`）。这是**有意为之**——按迁移纪律，除 import 外不改任何代码。
> 引用这些定理时需用**原命名空间** `Fate.X`，而不是 `FateWorld.Legacy.X`。

## 四、迁移过程中发现的问题

### 4.1 上游映射表严重失真

| 项 | 数字 |
|---|---:|
| 映射表登记模块 | 145 |
| 其中真的迁入 `命运-v2` | 126 |
| **登记了要迁但没迁** | **99**（含 36 个标记「A 原样迁入」） |
| 映射表完全没覆盖 | **697** |

**「A 原样迁入」这个动作标签本身就不成立**：实测 99 个应迁未迁里，
36 个标 A 的模块**全部**带 `import Fate.*`，在 `FateV2` 命名空间下根本无法原样编译。
⟹ 映射表的动作分类是按「代码质量」判的，**没考虑命名空间适配成本**。

详见 [`99-应迁未迁.md`](99-应迁未迁.md)。

### 4.2 素材夹本身可编译

好消息：842 个模块的依赖**完全自洽**，0 个悬空 import。
只有 2 个文件含 `sorry`。这说明旧代码库的内部一致性其实不差——
它的问题不是「坏」，而是「从未被纳入统一构建」。
