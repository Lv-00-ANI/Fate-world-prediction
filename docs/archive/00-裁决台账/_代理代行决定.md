## X-01 · 目录是「主题域」，不是「层」；架构规则改为「依赖图无环」

**背景**：迁移后看到 `Error → Loop` 与 `Loop → Error` 两个方向的边，
一度判定「两层互依，需接受或重构」。

### 实测推翻了那个判定

用 Tarjan 对 178 个模块、276 条内部依赖边求强连通分量：

| 项 | 结果 |
|---|---|
| SCC 总数 | **178**（每个模块自成一个 SCC） |
| 环（size > 1） | **0** |
| 自环 | **0** |

**⟹ 依赖图是 DAG，根本没有任何环。**

`Error → Loop` 16 条边、`Loop → Error` 16 条边，但**不构成回路**——只是两个主题域之间互相有边。

### 真正的发现：目录不是「层」

按最长路径分层（L0–L14），各主题域横跨的深度：

| 主题域 | 深度区间 | 模块数 |
|---|---|---|
| `Core` | L0–L2 | 6 |
| `Classical` | L0–L2 | 3 |
| `Bridge` | L0 | 3 |
| `Model` | L0–L2 | 5 |
| `Rules` | L0–L5 | 12 |
| `Modeling` | L0–L7 | 17 |
| `Loop` | L0–L13 | 29 |
| `Predict` | L0–L12 | 43 |
| `Error` | **L0–L14** | 53 |
| `Export` | L0 | 2 |
| `Meta` | L0–L1 | 5 |

**每个主题域都横跨几乎所有深度** ⟹ 「第 N 层只依赖上游」这个说法从来就不成立。

### 决定

| # | 决定 |
|---|---|
| **1** | **不重构目录**。前提（「有环」）是错的，没有环要破 |
| **2** | **目录正名为「主题域」**（domain），不再是「层」 |
| **3** | **架构不变量从「层间单向」改为「依赖图无环」**——这是**可验证**的，原来那条不可验证也不成立 |
| **4** | 新增门禁 **G11**：`_audit_cycle.py`，SCC size>1 或自环即失败 |
| **5** | 跨域依赖**允许**，但要**可见**：`_报告/依赖图.json` 记录全部跨域边 |

### 代价（如实记）

- 不能再声称「`Error` 只依赖上游」——但**从来也做不到**，只是以前没查；
- 「主题域」这个划分保留人类可读性，代价是它**不蕴含依赖方向**。

### 为什么这比「重构目录」好

- 重构目录（按深度分 15 层）会把 `Error` 的 53 个模块打散到 L0–L14，
  **概念上几乎无法阅读**（「L7 的误差」是什么意思？）；
- 而「无环」是真实成立、且能持续验证的性质。

**⟹ 保住了人类可读性，同时把架构承诺变成了可机检的事实。**

## X-09 · WholeState 暂用单一 Val（技术债，非降级）

**背景**：作者 D-023 D1 答「依赖类型」（Val : V → Type）。

**裁定**：**暂不改**，先保单一 Val : Type。

**理由**：
1. 依赖类型会波及 SCM.Model 的 F/Endo/Exo，进而波及 Predict/Export/Error 全线；
2. 现在**连一条端到端链都还没跑通**，先要「能跑」再要「类型精确」；
3. 依赖类型的主要收益是**多模态数据的类型安全**，而我们**还没有真实多模态数据**（作者 A2 已答「暂时无数据」）。

**将来怎么改**（写给未来）：
`lean
structure Model (V : Type u) (Val : V → Type u) (E : Type u) (Noise : Type u) where
  F   : (v : V) → ((w : V) → Val w) → E → Val v
  P_U : Noise
  graph : Option (Graph V)
`
Endo Val := (v : V) → Val v；Exo 不变。

**触发条件**：接入真实多模态数据时（A2 解除「无数据」之后）。

**登记为债，不是遗忘**：见本文件索引。

## X-10 · Demo 暂不迁移到泛型载体（技术债）

**背景**：专项 T3 交付了 Export/Carrier.lean（泛型载体 + ModalityG），
而 Demo/SyntheticRun.lean 的 3 个模态仍用旧 Modality + ExportVal。

**裁定**：**暂不迁移**。

**理由**：
1. demo 的 20+ 条定理把**具体数值**绑在旧接口上（7/5、13/10、-1/10…），迁移会破坏已验证的数值链；
2. 两套**并行并存**本身是有价值的证据：旧接口仍可用，泛型版不破坏它；
3. 「旧 ExportVal 是泛型的特例」已由 ExportCarrier_shared_fiber : ... := rfl 证明，
   **泛化没有丢东西**这一点已经落实，不必靠迁移 demo 来证明。

**触发条件**：接入真实多模态数据时（与 X-09 同时）。

## X-11 · **架构级事实**：ExportVal 类型层带三公理

**来源**：专项 T3 实测（2026-11-01），协调者独立复核。

`
'FateV2.Export.ExportVal' depends on axioms: [propext, Classical.choice, Quot.sound]
'Real'                    depends on axioms: [propext, Classical.choice, Quot.sound]
'Bool'                    does not depend on any axioms
`

**内容**：ExportVal 含 ExportVal.real : Real → ExportVal，而 Real 本身带三公理。
⟹ **类型层面**就带公理，**任何提到 ExportVal 的定理都不可能零公理**——
这与证明写法无关。

**后果（重要）**：

| 影响 | 说明 |
|---|---|
| **D-023 D1 的依据被加强** | 依赖类型（Val : V → Type）不只是「更精确」，它决定公理代价会不会传染 |
| **D-020 的边界要写清** | 「双界只在模型层」——现在有类型层证据：凡进 ExportVal 就出不了零公理 |
| **G4（核内零公理）的范围** | Core/ 不碰 Real，所以零公理成立；一旦引进 Real，必须换载体 |

**处置**：T3 把 §5 拆两半——BoolCarrier（零公理，证明泛型机制本身干净）
+ 完整 ExportVal 版（如实登记公理来源）。**这是正确做法**：机制与实例分开验证。
