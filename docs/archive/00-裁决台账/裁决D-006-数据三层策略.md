# D-006 · 数据三层策略（消融优先，嵌入与引用兜底）

> **裁决日期**：2026-10-28
> **裁决人**：作者
> **裁决原话**：「还是需要嵌入数据的　有些是直接描述某种和某种的那样子可能需要」
> **触发**：`裁决D-005` 的「数据不进入定理」过于绝对
> **设计稿**：[`07-IR设计/README.md`](../07-IR设计/README.md) §2.1、§五

---

## 一、修订了什么

D-005 的结论「数据不进入定理」**过强**，本裁决修正为三层策略：

| 层 | 条件 | 处理 | support 影响 |
|---|---|---|---|
| **① 消融**（首选） | 可形式化，**且消融后命题含义不变** | 转具体定理（support = ∅）或经验假设；数据归档 | 具体定理零增长 |
| **② 嵌入** | **消融会改变命题含义**，规模小 | `rat` / `vec` / `tup` / `ent` 直接写进定理 | 不增加（是语法） |
| **③ 引用** | 不可消融，规模大 | `ref DataId` + 档案登记 + hash | 不增加，但引入追溯义务 |

**判据一句话**：**消融掉之后，这条规则还是不是原来那条？**
是 → 消融。不是 → 嵌入或引用。

---

## 二、为什么必须有「嵌入」这一层

作者指出的情形：**有些规则直接描述「某种和某种」**——这类规则的**指称对象本身就是内容**。

| 例子 | 消融会怎样 | 结论 |
|---|---|---|
| 「A 与 B 同属性」（A、B 具体个体） | 变成「任意两实例」——**换了命题** | 必须能指称 A、B |
| 「这类与那类满足 R」 | 变成「任意两类」——**换了命题** | 必须能指称类别 |
| 「这类实例满足 P」 | 用 `all` 量化表达，**含义不变** | 可消融 |
| 「在 D 上误差 < 0.05」 | 无法脱离 D | 引用 |

⟹ **`Data` 必须保留 `ent`（实体/类别引用）与 `ref`（数据引用）两个构造子。**

---

## 三、新增的两个构造子

```lean
abbrev EntityId := String

inductive Data : Type
  | rat  (q : ℚ)
  | vec  (xs : List Data)
  | tup  (xs : List Data)
  | ent  (id : EntityId)     -- 实体 / 类别引用
  | ref  (id : DataId)       -- 数据集引用（须档案登记）
```

**义务**：
- 每个 `ent` 必须在 **`EntityTable`** 里有记录（否则是悬空指称）
- 每个 `ref` 必须在 **`DataArchive`** 里有记录且 hash 可校验

## 五、必须一起承接的代价

### 代价 1 · 悬空指称的风险

`ent "A"` 若在 `EntityTable` 里没有对应，规则就指向了不存在的东西。
⟹ **必须有 `ent` 的存在性检查**，且列为验收判据。

### 代价 2 · 「不增加 support」需要被验证

本裁决声称嵌入/引用不增加 support（因为它们是语法的一部分）。
但这只是设计意图——**若实现里把 `ref` 也记进 support，增长问题会回来**。
⟹ 验收判据 3b（support 无 data 字段）必须严格执行。

### 代价 3 · 嵌入与消融的边界要靠人判

「消融会不会改变含义」是**语义判断**，不能机器自动定。
⟹ 每次判定要留痕（验收判据 3c 已加）。
