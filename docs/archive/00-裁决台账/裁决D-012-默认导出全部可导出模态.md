# D-012 · 默认导出能导出的一切；边界是注册表，不是意义判据

> **裁决日期**：2026-10-28
> **裁决人**：作者

> **解决**：[`D-011`](裁决D-011-多模态含可推导模态.md) 尾#1（「有意义的模态」判据 → **不设**）

## 一、裁决内容（四条）

| # | 裁决 |
|---|---|
| **1** | **不设「有意义」判据**。默认**能导出什么就导出什么** |
| **2** | 导出的不是「挑选后的摘要」，而是**一个完整模型**的多模态表示 |
| **3** | 边界由**实现**决定：注册表里有多少个可执行的 `extract`，就能导出多少模态 |
| **4** | 但**允许限定范围**：可配置 include / exclude，输出受限子集 |

---

## 二、这解决了我原来的担心

我原来担心「能推导的模态无限多 ⟹ 输出不可控」。这个担心是**多余的**，因为：

> **能导出的模态 = 注册了 `extract` 的模态。**
> 也就是说，**边界不是数学上的"能推什么"，而是工程上的"实现了什么"。**

```lean
structure ModalityRegistry where
  mods : List Modality        -- 每条都带一个可执行的 extract

/-- 导出范围：空 = 全部（默认） -/
structure ExportScope where
  include : List ModalityId   -- 非空则只导这些
  exclude : List ModalityId   -- 排除这些

/-- **导出**：默认把注册表里能算的全算出来 -/
def export (reg : ModalityRegistry) (M : Model) (scope : ExportScope)
    : List (ModalityId × Value)
```

**⟹ 不需要「模态是否重要」这个判断。数据库里有几个视图，就导出几个视图。**

---

## 三、这个设计的好处

| 好处 | 说明 |
|---|---|
| **不引入主观判据** | 「什么算有意义」是价值判断，不该由系统做；系统只负责「算得出就给你」 |
| **可增量扩展** | 加一个模态 = 加一条 `extract`，导出集自动变大，不改任何既有代码 |
| **与 C2 自拓展一致** | 模态注册与算子注册是同一个机制（注册表驱动） |
| **受限导出仍然合法** | 用户想只看 3 个模态，就配 scope，不改变模型本身 |

---

## 四、必须一起承接的代价

### 代价 1 · 「完整模型」的体积

默认导出全部模态 ⟹ 一次导出的数据量可能远超原数据（每条序列都被展开成 6–7 个模态）。
⟹ 超大时用 `ref` + 档案（D-006 第③层），不是硬塞进定理。

### 代价 2 · 每个注册的 `extract` 都必须正确

既然「能导出就导出」，那**导出一个错的模态比不导出更糟**。
⟹ 每个 `extract` 都要有自己的验收（且其 σ 要能定）。

### 代价 3 · 受限导出必须被标记

若一次导出用了 scope 限制，结果必须是**受限子集**，不能声称「这是完整模型」。
⟹ 导出结果要带 `scope` 元数据。

### 代价 4 · 观测模态的完备性仍然要判

「能导出啥导出啥」不等于「原数据的模态一定在注册表里」。
⟹ D-011 的完备性要求（观测模态全覆盖）**仍然有效**，且要单独验。
