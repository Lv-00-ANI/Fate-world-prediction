# D-015 · 细节决策权下放到实现期，用四种策略之一解决

> **裁决日期**：2026-10-28
> **裁决人**：作者
> **裁决原话**：「很多细节实现中决定哪个最优哪个来　或者多路并行　或者找上层抽象　或者直接推广或者进行泛化」
> **作用**：这是一条**元裁决**——它规定了「设计期不决的东西，实现期怎么决」

---

## 一、裁决内容

设计文件**不必**在每一处细节上预先定死。凡属实现细节的分歧，**留到实现期**，并必须用下列**四种策略之一**解决：

| 策略 | 何时用 | 产物 |
|---|---|---|
| **① 择优** | 各方案可比较、且成本允许先试 | 一条实现 + 「为什么选它」的记录 |
| **② 多路并行** | 各方案优劣不明、且互不干扰 | 多条实现并存 + 统一接口 + 对照数据 |
| **③ 上层抽象** | 各方案是同一抽象的不同实例 | 一个抽象接口 + 若干实例（**这是首选，能一次性消灭分歧**） |
| **④ 推广泛化** | 某方案是另一方案的特例 | 泛化后的统一形式 + 特例作为实例 |

**优先级**：**③ > ④ > ② > ①**
（能抽象就别选，能泛化就别并行；实在不行才择优或并行。）

---

## 二、这对设计文件的意义

**设计文件的责任边界因此清晰**：

| 设计文件**必须**定 | 设计文件**不必**定 |
|---|---|
| 分层与铁律 | 具体数据结构的字段细节 |
| 各层的职责与接口 | 某个函数用哪种算法 |
| 跨层的类型契约 | 两个等价实现的取舍 |
| 不可证假设的登记 | 参数的具体取值 |
| 验收判据 | 优化器的选择 |

**⟹ 「彻底设计完」的标准不是「没有空白」，而是「每处空白都被标明属于哪一级、由哪条策略解决」。**

---

## 三、实施要求

每处未决细节必须在设计文件里**标注三级**：

```
[细节·策略③] Val 的类型：先试依赖类型 V → Type，若复杂度失控则退到统一 ℝ
```

格式：`[细节·策略<①|②|③|④>] 内容 + 初步倾向 + 退路`

**禁止**：
- ❌ 写「此处待定」而不给策略（那等于没管）
- ❌ 把实现细节伪装成设计决策（过度设计）
