## 二、这条裁决为什么是一次真正的统一

### 2.1 它让「不需要公理」有了技术落点

`C-005` 记录过一个长期张力：

| 说法 | 出处 |
|---|---|
| 「我并不认为需要公理」 | 作者第 32 轮原话 |
| 项目里却有 A1–A34「公理级假设」 | 净版第 8 章 |
| 「『不需要公理』是方向正确但被过度延伸的立场」 | `428:L72` 的评估 |

**本裁决之后，张力消失**：

> **底座无公理（纯 CIC）；凡被认为"像公理"的东西，一律是假设账本里的条目。**

「不需要公理」不再是一个需要辩护的**立场**，而是一条**架构事实**：
公理这个东西在系统里**根本没有特殊地位**——它和任何其它假设一样，是 `support` 里的一行。

### 2.2 它让 support 机制的价值最大化

`D-004` 设计的 `support.assumptions` 本来是为「未证前件」准备的。现在：

```
AssumptionId 包含：
  · propext              ← 三条基础公理
  · Classical.choice
  · Quot.sound
  · A1 … A34             ← 理论假设
  · 建模假设（构造忠实性等）  ← D-008
  · 数据消融产生的经验假设    ← D-005/D-006
```

**⟹ 一个统一的账本，管住了从「逻辑基础」到「数据经验」的全部前提。**

这是整个设计里**最干净的一处**：从最抽象的公理到最具体的脏数据，都在同一个 `Finset AssumptionId` 里。

## 三、必须一起承接的代价（这条最重）

### 代价 1 · 纯 CIC 用不了 Mathlib 的大部分

**这是决定性的工程后果。**

| 数学对象 | 是否依赖三条公理 | 后果 |
|---|---|---|
| `ℝ`（实数） | ✅ 依赖（Cauchy 完备化用 `Quotient`，序完备性用 `Classical.choice`） | **纯 CIC 下不可用** |
| `Measure`（测度论） | ✅ 依赖（σ-代数、Carathéodory 扩张） | **纯 CIC 下不可用** |
| `Topology` | 部分依赖 | 部分不可用 |
| `Finset` / `List` / `ℚ` | ❌ 不依赖 | ✅ 可用 |
| 归纳类型、`def`、`rfl` | ❌ 不依赖 | ✅ 可用 |

**⟹ 而我们的设计处处用到 `ℝ` 与 `Measure`**：误差剖面 `err : ℝ → ℝ`、外生律 `P_U : Measure U`、σ 是实数。

**纯 CIC 撑不起当前设计。**

### 代价 2 · 所以必须分两级（否则设计不成立）

```
┌─────────────────────────────────────────────────────────┐
│  经典外壳（可选层）                                       │
│  · 引入 propext / Classical.choice / Quot.sound 为**假设** │
│  · 提供 ℝ、Measure、拓扑                                 │
│  · 凡用它的定理：support.assumptions ⊇ {那三条}            │
│  · status 降为 conditional                                │
├─────────────────────────────────────────────────────────┤
│  构造性核（纯 CIC，无任何假设）                            │
│  · Term / Formula / Data / Judgment 的语法                │
│  · W ellSorted、substitute、quote                          │
│  · 四算子的语法操作                                        │
│  · 消融的记账                                              │
│  · 凡在此层证出的定理：support = ∅，status = proven        │
└─────────────────────────────────────────────────────────┘
```

**⟹ 裁决的真实含义**：**底座是纯 CIC；凡需要经典的，是"在纯 CIC 之上加了三条假设"**，而不是"底座自带三条公理"。

### 代价 3 · 门禁要改写

| 旧门禁 | 新门禁 |
|---|---|
| `#print axioms` ⊆ {propext, Classical.choice, Quot.sound} | **`#print axioms` 必须与 `support.assumptions` 一致** |

**新门禁更强**：
- 不是"只准用这三条"，而是"**用了什么就必须登记什么**"
- 构造性定理：`#print axioms` = ∅，且 `support = ∅`
- 经典定理：`#print axioms` = 实际用到的那几条，且 `support` 里**一字不差**地有它们

**⟹ 门禁从"白名单"升级为"账实相符"。**

### 代价 4 · 现有代码要分层盘查

`ProperFit` 那 149 个已编译模块，其定理**大多依赖经典**（因为用 `ℝ`/`Measure`）。
⟹ 不能直接搬进构造性核；必须先判「这一条到底依赖了什么」。

## 四、具体方案

### 4.1 假设账本里新增三条保留条目

```lean
-- 三条基础公理，作为**具名假设**登记（不是内核公理）
def axPropext    : AssumptionId := "propext"
def axChoice     : AssumptionId := "Classical.choice"
def axQuotSound  : AssumptionId := "Quot.sound"

/-- 经典外壳：凡导入此模块者，默认在其 support 里带上这三条 -/
structure ClassicalShell where
  assumptions : Finset AssumptionId := {axPropext, axChoice, axQuotSound}
```

### 4.2 两级定理的判定

```lean
/-- 构造性定理：不依赖任何假设 -/
def IsConstructive (j : Judgment) : Prop := j.support.assumptions = ∅

/-- 经典定理：恰好依赖那三条（或多一条都不行） -/
def IsClassicalOnly (j : Judgment) : Prop :=
  j.support.assumptions ⊆ {axPropext, axChoice, axQuotSound}
```

### 4.3 验收判据（新增 3 条）

| # | 判据 | 怎么验 |
|---|---|---|
| 12 | **构造性核里无任何公理依赖** | 对核内全部定理跑 `#print axioms`，结果必须为 `[]` |
| 13 | **`#print axioms` 与 `support.assumptions` 一致** | 逐定理对比两个集合（这是新门禁的核心） |
| 14 | 三条基础公理只以**假设**身份出现 | 全库检索 `axiom propext` 等原生声明，结果为 0 |
