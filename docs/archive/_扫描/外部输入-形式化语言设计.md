0. 总览

0.1 目标

构建一门以 CIC（归纳构造演算）为可信内核、内置 Lean 三条标准公理、为 Mathlib 量级数学库原生设计的通用形式化语言。

目标不是重写 Lean，而是在以下三点上做出明确取舍：

1. 内核极小可信：内核只做 CIC 类型检查，所有复杂功能（宏、类型类、终止检查、层级求解）在前端。
2. 公理可选分层：三条公理作为模块导入，构造性用户不导入则完全不可见。
3. 声明是一等原子：编译、缓存、失效、调度统一以声明为单位，模块只是声明的命名集合；支持"只编译一条定理"这种粒度的增量编译。

0.2 核心分层

```
用户源码
  ↓  parser / 宏展开
语法树
  ↓  elaborator（隐式参数、unification、类型类、coercion、终止检查）
已填充的 CIC 项
  ↓  kernel typechecker（可信、极小）
通过检查的声明与环境
  ↓  声明级模块系统 / 声明级编译驱动 / 内容寻址缓存
产物：sig / body / meta 三类声明对象 + 模块索引
  ↓  解释器 / 编译器 / 文档 / LSP
用户与工具链
```

0.3 一句话总结

内核极小可信；公理可选分层；声明是编译、缓存、失效、调度的统一原子；模块只是声明集合的命名入口；证明体公开但不传播失效，定义体公开且按朴素闭包传播（可 opaque 收紧）；单模块、多模块、单定理、多定理编译统一归约为"目标声明集合 + 传递闭包"。

1. 设计信条与基本原则

1.1 六条信条

1. 内核极小：内核只做 CIC 类型检查、定义性相等、归纳类型合法性、层级约束一致性。不承担宏、类型类、coercion、终止检查启发式、层级求解、证明搜索、模块解析。
2. 公理可选：三条公理作为标准库模块，不导入则保持纯构造性。公理以 axiom 形式存在，产生 Eq 证明，不进入定义性相等。
3. 声明是一等原子：编译、缓存、失效、调度的最小单位是声明，不是模块。模块只是声明的命名集合与索引入口。
4. 默认公开，但区分证明体与定义体：证明体公开（可引用、可打印）但不参与转换检查，修改不传播；定义体公开且参与转换检查，修改按朴素闭包传播；opaque 可显式收紧。
5. 库规模是一等设计约束：模块系统、构建系统、依赖粒度从第一天就为大规模型库设计，而非事后补丁。
6. 朴素依赖闭包 + 定理例外：依赖传播用最简单的朴素闭包，唯一例外是定理证明体不传播（proof irrelevance）。

1.2 与前代设计的对比

维度 Lean 4 本设计
内核 C++ 内核 + Lean 元编程 极小 CIC 内核（参考 Lean4Lean / leanr-core）
公理 标准库导入 标准库导入，分层设计
模块系统 模块级 import，公开/私有作用域 声明级依赖，模块只是命名集合
编译单元 模块 声明（模块/多模块/单声明/多声明统一模型）
依赖粒度 模块图 声明图（每声明携带依赖元数据）
证明体 私有（默认） 公开但不传播
定义体 私有（默认） 公开且传播，可 opaque
失效传播 作用域边界 is_dirty 唯一入口，按 DepEntry.body-hash 存在性判定
编译目标 模块 module / modules / decl / decls 统一归约

1.3 关键设计决策（前置定死）

这些决策在后续章节中详细展开，但在此集中列出，因为它们后期最难改：

1. 三条公理是 axiom 形式，不进入定义性相等。
2. proof irrelevance 进入定义性相等。
3. Prop 不可预测（imax 规则）。
4. 内核支持层级变量与约束，求解器在前端。
5. 支持索引归纳族。
6. Lean 式 singleton elimination。
7. 函数 η 进入定义性相等。
8. let 作为内核原语。
9. 语法严格正性起步。
10. WHNF + 惰性 delta 转换检查。
11. 声明级依赖元数据：统一 deps 集合 + DepEntry.body-hash 存在性判定。
12. 定理证明体变化不传播；def / abbrev / rec / inductive 变化按朴素闭包传播；opaque / axiom / ctor 体不传播。
13. 内核转换检查必须确定性展开（保证元数据可复现）。
14. DeclId = 限定名 + 稳定 UUID 双标识，重命名不算签名变化。
15. 缓存键不包含依赖哈希（依赖由 DepEntry 逐条判定）。

2. 内核层：CIC 类型规则

2.1 语法

```
项   t ::= x | Sort_l | Π (x : A), B | λ (x : A), t
         | t u | let x : A := t in u
         | c | I | ctor_i | rec_I
层级 l ::= 0 | u | succ l | max l l | imax l l
上下文 Γ ::= · | Γ, x : A
环境   E ::= · | E, (c : A) | E, (c : A := t) | E, (c : A opaque)
           | E, Inductive(I, params, indices, ctors, sort)
           | E, Quot(...)
```

· Sort_0 = Prop，Sort_{succ l} = Type_l。
· u 为层级变量。
· c 为常量（定义、定理、公理、构造子、递归子）。
· I 为归纳类型。
· rec_I 为 I 的递归子。

决策点 1：let 作为内核原语，转换中透明展开。理由：保留共享，避免重复展开；规则简单（一条 let 转换规则）。

公理常量：propext、Classical.choice、Quot.sound 以 (c : A) 形式入环境，无定义体，不可 δ 展开。

Quot 原语：Quot 是内核原语（非普通归纳类型），因为 Quot.mk 与 Quot.sound 需要特殊处理。语法层提供 quotient / setoid 声明，展开为内核 Quot 原语。

2.2 判定关系

```
Γ ⊢ t : T                类型检查
Γ ⊢ t ≡ t' : T           定义性相等（带类型）
Γ ⊢ l₁ ≤ l₂              层级约束
E; Γ ⊢ 约束集可满足        约束一致性检查
```

关键：转换检查接口必须携带类型（或维护类型缓存），因为 proof irrelevance 需要判断"两个项是否都是某个 Prop 的证明"。

决策点 2：转换检查用 WHNF + 惰性 delta，不做全规范化。理由：规范化可能指数爆炸；Lean/Coq 都用转换检查算法；这是性能与正确性的唯一现实选择。

2.3 类型规则

2.3.1 变量 / 宇宙 / 常量

```
x : A ∈ Γ
──────────
Γ ⊢ x : A

──────────────────────
Γ ⊢ Sort_l : Sort_{succ l}

(c : A) ∈ E
───────────
Γ ⊢ c : A

(c : A := t) ∈ E
─────────────────
Γ ⊢ c : A
```

2.3.2 函数类型 Π

```
Γ ⊢ A : Sort_u    Γ, x : A ⊢ B : Sort_v
────────────────────────────────────────
Γ ⊢ Π (x : A), B : Sort_{imax u v}
```

其中：

· imax u 0 = 0
· imax u (succ v) = max u (succ v)

决策点 3：Prop 不可预测。当 B : Prop（即 v = 0）时，整个 Π 在 Prop，无论 A 在哪层。这是 imax 规则的来源，也是 Prop 能编码高阶逻辑的基础，是 Mathlib 式库可移植的前提。

2.3.3 抽象 / 应用 / 转换

```
Γ ⊢ A : Sort_u    Γ, x : A ⊢ t : B    Γ ⊢ Π (x : A), B : Sort_v
────────────────────────────────────────────────────────────────
Γ ⊢ λ (x : A), t : Π (x : A), B

Γ ⊢ f : Π (x : A), B    Γ ⊢ a : A
──────────────────────────────────
Γ ⊢ f a : B[x := a]

Γ ⊢ t : A    Γ ⊢ A ≡ B : Sort_u    Γ ⊢ B : Sort_u
──────────────────────────────────────────────────
Γ ⊢ t : B
```

2.3.4 let

```
Γ ⊢ A : Sort_u    Γ ⊢ t : A    Γ, x : A ⊢ u : B
────────────────────────────────────────────────
Γ ⊢ let x : A := t in u : B[x := t]
```

let 在转换中透明：let x := t in u ≡ u[x := t] : B。实现上懒惰展开以保留共享。

2.4 定义性相等 ≡

≡ 是带类型的等价关系：Γ ⊢ t ≡ t' : T。

2.4.1 结构规则

```
Γ ⊢ t ≡ t' : Π (x : A), B    Γ ⊢ a ≡ a' : A
──────────────────────────────────────────────
Γ ⊢ t a ≡ t' a' : B[x := a]
```

以及 Π、λ、Sort 的逐层比较规则（略）。

2.4.2 β

```
Γ ⊢ (λ (x : A), t) a ≡ t[x := a] : B[x := a]
```

2.4.3 δ（常量展开）

```
(c : A := t) ∈ E    c 非 opaque    c 非公理
────────────────────────────────────────────
Γ ⊢ c ≡ t : A
```

opaque 定义与公理不展开，作为中性常量参与比较。

决策点 13：δ 展开必须确定性——按声明名排序、按固定时机展开，不依赖哈希表遍历顺序。这保证 expand 路径可复现（虽然路线 B 不记录 expand-deps，但确定性展开仍是内核可信性的加分项）。

2.4.4 ι（递归子归约）

```
Γ ⊢ rec_I ... (ctor_i ...) ... ≡ minor_i ... : motive (ctor_i ...)
```

决策点 11：仅在 major premise 的 WHNF 是构造子时触发。中性 major premise 不归约。这保证转换检查可判定。

2.4.5 η（函数）

```
Γ ⊢ f : Π (x : A), B    x ∉ FV(f)
──────────────────────────────────
Γ ⊢ λ (x : A), f x ≡ f : Π (x : A), B
```

决策点 5：函数 η 进入定义性相等。实现上：一边是 λ、另一边是中性项时，把中性项应用到新变量再比较。理由：与 Lean 一致，λ x, f x 与 f 定义性相等，简化许多证明；是 Lean 生态兼容的前提。

2.4.6 let

```
Γ ⊢ let x : A := t in u ≡ u[x := t] : B[x := t]
```

2.4.7 proof irrelevance

```
Γ ⊢ p : P    Γ ⊢ q : P    Γ ⊢ P : Prop
──────────────────────────────────────
Γ ⊢ p ≡ q : P
```

决策点 6：proof irrelevance 进入定义性相等。这是整个编译架构的基石：

· 任何两个 Prop 的证明在转换中直接相等，不比较结构、不展开证明体；
· 定理的证明体永远不进入转换检查；
· 修改定理证明体不改变任何下游的转换判定；
· 下游引用定理只需其类型签名，不需证明体；
· 这是路线 B 中"定理证明体变化不传播"的语义基础。

决策点 7：三条公理产生的是命题相等（Eq 证明），不是定义性相等。理由：

· 公理形式保持转换检查可判定性（不依赖证明搜索）；
· 与"公理可选"设计一致；
· 使用 propext 后需要 Eq.rec / transport，前端提供 by extensionality 策略自动化。

2.4.8 等价关系性质

≡ 是自反、对称、传递的等价关系，且对所有类型规则同余。

2.5 三条公理

2.5.1 声明

```
axiom propext          : (a ↔ b) → a = b
axiom Classical.choice : Nonempty α → α
axiom Quot.sound       : r a b → Quot.mk r a = Quot.mk r b
```

三者均为无定义体的常量，入环境后：

· 不可 δ 展开；
· 产生的项是 Eq 类型的证明，因此受 proof irrelevance 约束——但公理本身作为常量是中性项，其应用不产生新的定义性相等。

2.5.2 关键性质

· propext h 的类型是 a = b，是 Prop 的证明；两个 propext 证明在转换中相等，但 propext h 与 Eq.refl 不定义性相等。使用 propext 后需 Eq.rec / transport。
· Quot.mk r a 与 Quot.mk r b 在转换中不相等，即使 r a b；Quot.sound 只给出 Eq 证明。
· 这保证转换检查不依赖证明搜索，可判定性不受公理影响。

2.5.3 Quot 的原语地位

Quot 是内核原语，因为 Quot.mk 与 Quot.sound 需要特殊处理：

· Quot 的消去子只允许消去到 Prop 或满足条件的 Type（与 Quot.sound 一致性）；
· 语法层提供 quotient / setoid 声明，展开为内核 Quot 原语。

2.5.4 可计算性

使用三条公理的声明标 noncomputable；编译器拒绝编译含公理项的代码生成；解释器给出"无计算内容"显式错误。

2.6 归纳类型

2.6.1 声明

```
Inductive I (params) (indices) : Sort_u :=
  | ctor_1 : T_1
  | ...
```

决策点 8：支持索引归纳族（如 Vec : Nat → Type、Eq : α → α → Prop）。理由：否则 Eq、Vec、Fin 无法原生表达，Mathlib 无法移植。

2.6.2 严格正性

决策点 9：语法严格正性起步。

I 在构造子类型 T_i 中只允许出现在严格正位置：

· T_i 中 I 不作为函数参数类型出现；
· 允许 I 出现在 Π 的返回类型位置；
· 起步阶段不允许嵌套归纳类型（如 W 类型），作为后续扩展。

2.6.3 递归子

```
rec_I : Π (params) (motive : I params indices → Sort_v)
        (minor_1 : ...) ... (major : I params indices),
        motive major
```

minor_i 的类型由构造子 ctor_i 与 motive 生成，递归位置对应递归子调用。

2.6.4 大消去（singleton elimination）

决策点 10：Lean 式规则。

· I 在 Prop 时，motive 的目标 Sort_v：
  · v = 0（消去到 Prop）：总是允许；
  · v > 0（消去到 Type）：仅当 I 是 subsingleton 归纳类型——即 I 的所有构造子的所有参数类型都在 Prop 中（没有 Type 中的数据字段）。
· I 在 Type 时：无限制。

关键例子：Eq : α → α → Prop 的唯一构造子 refl : Eq a a 无额外数据字段，因此 Eq.rec 允许消去到 Type。这是 Mathlib 大量使用 Eq.rec 的前提，必须保证。

一致性保障：禁止从 Prop 中提取非平凡数据（如从 Nonempty α 直接提取 α），这正是 Classical.choice 作为公理存在的原因。

2.6.5 ι 归约

```
rec_I params motive minors (ctor_i args) ≡ minor_i args (递归调用)
```

仅当 major premise 的 WHNF 是构造子时触发。

2.7 宇宙层级

2.7.1 层级表达式

```
l ::= 0 | u | succ l | max l l | imax l l
```

决策点 4：内核支持层级变量与约束，求解器在前端。

2.7.2 约束

```
l₁ ≤ l₂
```

内核维护约束集，新增约束时检查与已有约束可满足（一致性）。完整的层级求解（如 max/imax 的最一般解）在前端完成；内核只做约束一致性检查，保证类型检查不因层级矛盾而崩溃。

2.7.3 累积性

Type_l : Type_{succ l}，且 Type_l ≤ Type_{succ l} 的累积性通过转换规则体现（Γ ⊢ t : Type_l 且 l ≤ l' 则 Γ ⊢ t : Type_l'）。Prop 不参与累积到 Type。

2.8 转换检查算法

```
conv(Γ, t, u, T):
  1. 若 T 的 WHNF 是 Prop 且 t、u 均为该 Prop 的证明：
       返回 true                    # proof irrelevance
  2. t' ← whnf(Γ, t); u' ← whnf(Γ, u)
  3. 若 t'、u' 均为 Sort：比较层级约束
  4. 若 t'、u' 均为 Π：逐层比较 domain 与 codomain
  5. 若 t' 为 λ、u' 非 λ：η 展开 u'，递归
     若 u' 为 λ、t' 非 λ：对称
  6. 若 t'、u' 均为 λ：比较 body
  7. 若 t'、u' 均为应用：比较 head 与 argument
  8. 若 t'、u' 均为常量：若可 δ 展开则展开后递归；否则比较常量名
  9. 若 t'、u' 均为 let：展开后递归（或先比较绑定）
  10. 若 t' 为 rec 且 major 为构造子：ι 归约后递归
  11. 否则：t' 与 u' 结构不同，返回 false
```

whnf 执行 β、δ（非 opaque、非公理）、let、ι（构造子 major）、η 的惰性展开，不展开 proof irrelevance（由 conv 第 1 步处理）。

决策点 13 的实现约束：WHNF 按固定顺序（β → let → ι → δ → η），δ 展开按声明名排序，不依赖哈希表遍历顺序。

2.9 内核边界再确认

内核不做：

· 宏展开、隐式参数、unification、类型类合成、coercion；
· 终止检查启发式（只检查已生成的递归子）；
· 层级求解（只做约束一致性检查）；
· 证明搜索（公理不进入 ≡）；
· 命名空间、模块解析。

内核只做：

· 类型检查（2.3 节）；
· 定义性相等（2.4 节，含 proof irrelevance）；
· 归纳类型合法性（严格正性、singleton elimination）；
· 层级约束一致性。

2.10 与编译架构的衔接

这套规则直接支撑第 7、8 节的编译模型：

编译架构要求 内核规则支撑
证明体修改不触发下游重编译 2.4.7 proof irrelevance：证明体永不进入 ≡，下游只依赖类型签名
定义体修改传播 2.4.3 δ：定义体参与转换，下游可能依赖
opaque 定义不传播 2.4.3：opaque 不展开，作为中性常量
公理可选、不影响转换可判定性 2.5.2：公理不产生定义性相等，转换不依赖证明搜索
商类型 API 可用 2.5.3：Quot 原语 + Quot.sound 公理
Eq.rec 消去到 Type 2.6.4：singleton elimination 允许 Eq 大消去

3. 公理层：三条公理的分层设计

3.1 原则

三条公理不属于 CIC 核心类型规则，作为可显式启用的原始常量 / 标准库模块存在。不导入则保持纯构造性。

3.2 三条公理

公理 逻辑作用 工程处理
propext 逻辑等价 → 命题相等 作为 axiom 导入；语言层提供 by extensionality 策略
Classical.choice 从存在性证明提取数据 作为 axiom；使用处标 noncomputable
Quot.sound 商类型可靠性 内核保留 Quot 原语；语法层提供 quotient / setoid 声明

3.3 可计算性边界

noncomputable 是语言级标记：

· 编译器拒绝编译含公理项的代码生成；
· 解释器给出"无计算内容"显式错误；
· noncomputable 变化只重编译自身，不传播给下游（下游是否需要 noncomputable 由自身类型检查决定）。

3.4 构造性默认

默认构造性；import Classical 后获得排中律等派生定理。三条公理之上再叠经典数学层（商类型 API、集合论式推理），作为内置可选层随语言分发，逻辑上仍独立于内核。

3.5 公理形式的关键性质

· propext h 的类型是 a = b，是 Prop 的证明；两个 propext 证明在转换中相等，但 propext h 与 Eq.refl 不定义性相等。使用 propext 后需 Eq.rec / transport，前端提供 by extensionality 自动化。
· Quot.mk r a 与 Quot.mk r b 在转换中不相等，即使 r a b；Quot.sound 只给出 Eq 证明。
· 这保证转换检查不依赖证明搜索，可判定性不受公理影响。

5. 可见性与转换规则

5.1 核心区分：证明体 ≠ 定义体

· 证明体：语法上公开（可引用、可打印），但不参与定义性相等判定（proof irrelevance），修改证明体不触发下游重编译。
· 定义体：默认公开，参与 delta reduction，修改定义体可能触发下游重编译，除非标 opaque / @[irreducible]。

5.2 完整规则表

项 默认可见性 参与转换检查 修改触发下游重编译
定理证明体 公开（可引用/打印） 否 否
普通定义体 公开 是（delta） 是，除非 opaque
abbrev 体 公开 是 是
显式 private 项 私有 视项而定 否
显式 opaque 定义 公开 否 否
公理 公开 否（中性常量） 否（无体）
构造子 公开 否 否（无体）

5.3 缓解机制

1. 声明级依赖闭包精确记录“实际 delta 展开的声明”，而非笼统模块依赖（路线 B 下由 DepEntry.body-hash 存在性表达）。
2. opaque / @[irreducible] 显式标记：想收紧的定义体可标记不透明。
3. 模块索引与声明体分离：加载模块索引不等于加载所有体。
4. 展开集合通常远小于导入集合（Mathlib 数据显示平均只用导入作用域的约 1.6%）。

6. 模块系统：声明是一等原子

6.1 根问题

CIC 的基本依赖类型是反模块化的：证明体在逻辑上无关紧要，但传统模块系统把证明体当同等数据传递，导致改一个证明内部步骤就触发下游全量重编译。

6.2 设计结论

· 模块不是特殊实体，只是"声明集合"的一种命名方式。
· 声明是编译、缓存、失效、调度的统一原子。
· 每条声明在产物中携带自己的依赖元数据与哈希。

6.3 依赖的统一记录

决策点（路线 B）：每个声明记录一套统一的依赖集合，不区分 sig-deps / expand-deps / body-deps。每个 DepEntry 携带：

· 被依赖声明的 stable-id；
· 被依赖声明的 sig-hash 快照；
· 可选 body-hash 快照——是否存在由被依赖对象的 kind 决定。

关键规则：DepEntry.body-hash 是否存在，由被依赖对象的 kind 决定，而非由本声明决定。

· 依赖一个 theorem → body-hash = None；
· 依赖一个 def → body-hash = Some(...)；
· 依赖一个 opaque → body-hash = None；
· 依赖一个 axiom / ctor → body-hash = None；
· 依赖一个 abbrev → body-hash = Some(...)；
· 依赖一个 rec → body-hash = Some(...)；
· 依赖一个 inductive → body-hash = None（变化走 sig-hash）。

这样，"体变化是否传播"被编码在依赖条目里，失效判定不需要回查被依赖对象的 kind，只读本对象 meta 即可。

6.4 传播语义

被依赖对象 kind 签名变化传播 体变化传播
theorem 是 否（proof irrelevance）
def 是 是（δ 展开）
abbrev 是 是（δ 展开）
opaque 是 否（不展开）
axiom 是 —（无体）
inductive 是（走 sig-hash） —（视为签名一部分）
ctor 是 —（无体）
rec 是 是（行为由 I 与 ctors 决定）

7. 编译架构：目标 → 声明集合 → 传递闭包

7.1 统一模型

一切编译粒度归约到同一模型：

```
目标（root set）= 用户指定的声明集合
编译闭包 = 目标 ∪ 目标的传递依赖
编译单元 = 闭包中的每个声明
```

· 单模块：root = 该模块全部声明。
· 多模块：root = 这些模块全部声明的并集。
· 单定理：root = 一条声明。
· 多定理：root = 多条声明的并集。

模块不再有特殊地位，只是"声明集合"的命名入口。

7.2 编译流程

```
1. 解析目标（模块 / 多模块 / 单声明 / 多声明）
2. 展开为 root 声明集合
3. 计算传递闭包：
   - 从 meta 读取每个声明的 deps
   - 求闭包，得到待处理声明 DAG
4. 拓扑排序，按声明调度
5. 对每个声明：
   - 若缓存键命中 → 复用对象
   - 否则类型检查，产出 sig / body / meta 对象
6. 输出目标产物（模块索引 或 单声明对象）
```

要点：闭包计算依赖"声明的依赖集合"元数据，而非"模块 import 图"。

7.3 产物布局（按声明粒度）

```
.build/<toolchain-hash>/
  decls/
    Foo/Bar/myTheorem.sig     # 类型签名（下游引用只需这个）
    Foo/Bar/myTheorem.body    # 证明体 / 定义体
    Foo/Bar/myTheorem.meta    # 依赖集合、哈希、kind
  modules/
    Foo/Bar.idx               # 模块 → 声明列表索引（轻量，不含体）
```

· 单定理编译：只读写该声明三对象及闭包内缺失对象。
· 模块编译：批量产出该模块所有声明对象 + 模块索引。
· 模块索引很轻，可快速加载。

7.4 缓存键

```
cache-key(d) = H(
  规范化后的类型项,
  规范化后的体项,
  toolchain-hash
)
```

决策点 15：缓存键不包含依赖哈希。依赖由 DepEntry 逐条判定。

理由：若缓存键包含依赖哈希，传递失效会导致"改一个底层定义，所有签名哈希变，缓存大面积失效"。不包含时，失效判定可以逐条精确，而不是哈希级联。

7.5 失效传播规则（is_dirty 唯一入口）

```
is_dirty(d, current):
  if d.source-changed:                 # 源码自上次编译后变了
      return true
  for e in d.deps:
      cur = current(e.decl-id)
      if e.sig-hash ≠ cur.sig-hash:
          return true
      if e.body-hash is Some(h) and h ≠ cur.body-hash:
          return true
  return false
```

语义：

· e.body-hash 为 None 时，被依赖对象的体变化永远不触发 d 重编译。这自动实现了定理、opaque、公理、构造子、归纳类型的体不传播。
· e.body-hash 为 Some 时，被依赖的 def / abbrev / rec 体变化触发 d 重编译。

7.6 增量编译流程

```
1. 用户修改若干声明 → 标记为 source-changed
2. 工作列表 W = 所有 source-changed 声明
3. while W 非空:
     d = W.pop()
     重新编译 d，得到新的 sig-hash / body-hash / deps
     对所有 deps 中含 d 的声明 x:
       若 is_dirty(x, current): W.push(x)
4. 输出重编译后的声明对象
```

这是标准的基于依赖图的工作列表算法。is_dirty 是唯一判定入口，不需要单独的"反向失效"逻辑。

7.7 缓存复用条件（对应规则 1.4）

```
可复用缓存 ⟺ 声明源码未变 ∧ 所有 deps 条目中：
              e.sig-hash 与 current 一致
              且 e.body-hash（若存在）与 current 一致
```

这正是 is_dirty 的否定。

7.8 并行与调度

· 调度单位是声明，不是模块。
· 声明 DAG 的拓扑层内可并行。
· 模块级编译只是"一次性把多个 root 声明入队"。
· 单定理编译时，若闭包内大部分声明已缓存，实际只检查这一条。

7.9 命令行与 API

```
lang build --module Foo.Bar              # 模块 + 全部依赖
lang build --modules Foo.Bar,Baz.Qux     # 多模块 + 并集闭包
lang build --decl Foo.Bar.myTheorem      # 单定理 + 全部依赖
lang build --decls Foo.Bar.thm1,Foo.Bar.thm2
```

API：

```
compile(targets: DeclSet | ModuleName | DeclName) -> Artifact
```

语义统一：目标展开为声明集合，编译其传递闭包，按声明粒度调度与缓存。

8. 元数据格式（路线 B 定稿）

8.1 路线 B 核心规则

朴素依赖闭包 + 定理例外。

· 每个声明记录全部依赖（签名依赖 + 体依赖合并为一个集合）。
· 声明自身变化 → 沿依赖边反向传播，所有（传递）依赖它的声明重编译。
· 声明未变且全部依赖未变 → 复用缓存。
· 唯一例外：定理的证明体变化不传播给下游（proof irrelevance），但定理自己仍会因证明体源码变化而重编译。
· opaque 定义的体变化同样不传播。
· def / abbrev / rec 的体变化按朴素闭包传播。

8.2 哪些 kind 的"体"参与传播

kind 有体 体变化传播给下游 理由
theorem 有（证明体） 否 proof irrelevance：下游只依赖类型签名
def 有 是 体参与 δ 展开，下游类型检查可能依赖
abbrev 有 是 同上
opaque 有 否 体不展开，下游只依赖签名
axiom 无 — 无体
inductive 构造子列表 是（通过 sig-hash） 构造子是接口的一部分
ctor 无 — 只有类型签名
rec 生成体 是 行为由 I 与 ctors 决定

简化：只有 def / abbrev / rec 的 body-hash 进入下游的依赖记录；theorem / opaque / inductive / axiom / ctor 的 body-hash 只用于自身缓存键。

8.3 声明对象

```
DeclMeta {
  -- 身份
  decl-id      : DeclId            -- 限定名 + 稳定 UUID
  stable-id    : UUID              -- 重命名不变化的稳定标识
  kind         : Kind              -- theorem | def | abbrev | opaque | axiom
                                   -- | inductive | ctor | rec
  module       : ModuleName        -- 仅索引，不参与依赖判定

  -- 依赖（统一集合）
  deps         : List<DepEntry>    -- 签名依赖 + 体依赖，合并

  -- 哈希
  sig-hash     : Hash              -- 规范化类型项（名字解析为 stable-id）
  body-hash    : Option<Hash>      -- 有体的声明才有；axiom/ctor 为 None
  meta-hash    : Hash              -- 本对象除哈希外字段的规范化哈希

  -- 可计算性
  noncomputable: Bool

  -- 扩展区（不参与失效）
  doc          : Option<String>
  attrs        : List<Attr>
  source-span  : Option<Span>
}
```

8.4 依赖条目

```
DepEntry {
  stable-id    : UUID              -- 被依赖声明的稳定标识
  decl-id      : DeclId            -- 限定名（用于错误信息与文档）
  sig-hash     : Hash              -- 被依赖声明签名哈希的快照
  body-hash    : Option<Hash>      -- 仅当被依赖声明 kind ∈ {def, abbrev, rec} 时存在
}
```

决策点 1：DepEntry 内嵌哈希快照。理由：失效判定只需读本对象的 meta，不必回查被依赖对象的当前哈希，判定 O(依赖数)；且元数据自包含，适合分布式缓存。

8.5 标识符与重命名

决策点 4：DeclId 用限定名 + 稳定 UUID 双标识。

标识 用途
decl-id（限定名） 人类可读、与源码一致、错误信息、文档
stable-id（UUID） 失效判定、依赖记录、重命名不失效

决策点 5：重命名不算签名变化。重命名只更新限定名映射，不触发重编译。提供 --strict-rename 开关。

理由：重命名在数学库演进中极常见，严格模式会让 Mathlib 式库无法维护。

8.6 哈希方案

决策点 6：哈希对象。

```
sig-hash  = H(规范化类型项, stable-id 列表)
body-hash = H(规范化体项, stable-id 列表)
meta-hash = H(除哈希外所有字段，按规范化序列化)
```

· 规范化项：de Bruijn 索引、层级表达式规范形、let 不展开、名字解析为 stable-id。
· 不哈希源码位置、文档、属性（扩展区不参与失效）。
· 哈希算法：BLAKE3（性能敏感）或 SHA-256。

决策点 7：sig-hash 不包含依赖的哈希。依赖关系由 DepEntry 表达。

8.7 序列化格式与版本

决策点 8：二进制为主，文本 dump。

· 二进制（Cap'n Proto / FlatBuffers / 自定义 TLV）：零拷贝读取，加载模块索引时只读 decl-id、kind、sig-hash，不读 deps 列表。
· 文本 dump：--dump-meta 输出 S-expression，用于对拍与调试。

决策点 9：版本与兼容。

· 每个 .meta 头部记录 format-version 与 toolchain-hash；
· format-version 不匹配：拒绝加载，触发重编译；
· toolchain-hash 不匹配：缓存失效（内核规则变化可能改变转换判定）；
· 提供向前兼容读取：新格式读旧格式时，缺失字段用保守默认（如 deps 缺失则视为"空依赖 + 必须重编译"；body-hash 缺失视为 None，保守但安全）。

8.8 失效判定算法

给定声明 d 的旧 meta 与新 meta（重编译后），判定哪些下游失效：

```
invalidate(d):
  changed-sig  = (old.sig-hash  ≠ new.sig-hash)
  changed-body = (old.body-hash ≠ new.body-hash)
  changed-meta = (old.meta-hash ≠ new.meta-hash)

  if changed-sig:
    对所有 DepEntry.stable-id = d 且出现在其 deps 的下游：失效
  if changed-body and d.kind ∈ {def, abbrev, rec}:
    对所有 DepEntry.stable-id = d 且出现在其 deps 的下游：失效
  if changed-body and d.kind ∈ {theorem, opaque}:
    不传播
  if changed-meta only:
    不传播（扩展区变化）
```

决策点 10：定理的 body-hash 变化完全不传播。

· 是：依赖 proof irrelevance，下游只依赖 sig-hash。这是"证明体修改不触发重编译"的落地。
· 例外：若下游显式引用了定理的证明项（如 theorem t := by exact thm 把 thm 的证明体嵌入自己的证明体），则 thm 进入下游的 deps，但其 DepEntry.body-hash 为 None，所以仍不触发下游转换判定变化——只是下游重编译时需要 thm 的 body 可用。这要求缓存保留定理 body，即使它不传播失效。
· 建议：完全按上述规则，并在文档中明确"定理 body 可被引用但永不传播失效"。

8.9 边界情况确认

8.9.1 定理 T 的证明体引用了定义 D，D 的体变了

· T 的 deps 中含 D，D 的 kind 是 def，所以 T 的 DepEntry 中 D 的 body-hash 为 Some。
· D 体变 → T dirty → T 重编译。
· T 重编译后若 sig-hash 未变 → T 的下游不 dirty。

正确：T 的证明体需要重新检查（因为 D 可能被展开），但 T 的类型未变，下游不受影响。

8.9.2 定理 T 的证明体引用了定理 S，S 的证明体变了

· T 的 deps 中含 S，S 的 kind 是 theorem，所以 T 的 DepEntry 中 S 的 body-hash 为 None。
· S 体变 → T 不 dirty。

正确：proof irrelevance 下 S 的证明体不展开，T 的证明体引用 S 时只看 S 的类型，S 体变化不影响 T。

8.9.3 定理 T 的证明体源码变了，但类型没变

· T 自身 source-changed → T 重编译。
· T 的 sig-hash 未变 → 下游不 dirty。

正确：这是路线 B 保留的最大收益。

8.9.4 opaque 定义 O 的体变了

· O 自身 source-changed → O 重编译。
· 引用 O 的声明，其 DepEntry 中 O 的 body-hash 为 None → 不 dirty。

正确：opaque 的体不展开，下游只依赖签名。

8.9.5 定义 D 的体变了，签名没变

· D 重编译。
· 所有 deps 中含 D 的声明，其 DepEntry 中 D 的 body-hash 为 Some 且与 current 不一致 → 全部 dirty。

正确：朴素闭包，非定理的体变化全量传播。

8.9.6 归纳类型 I 的构造子列表变了

· I 的 sig-hash 变化（构造子列表是签名的一部分）。
· 所有 deps 中含 I 的声明 dirty。

正确：归纳类型的构造子是接口的一部分。

8.9.7 rec 的生成体变了（因为 I 或 ctors 变了）

· rec 的 body-hash 变化。
· 所有 deps 中含 rec 的声明 dirty。

正确：rec 的行为由 I 与 ctors 决定，其变化传播。

8.10 与工具链的衔接

· LSP：读 .meta 扩展区（doc、span、attrs），不读 .body；增量重载只重读变化的 meta。
· 文档生成：只读 .sig + 扩展区，不触碰 .body。
· 编译器：读 .body + noncomputable 标记；含公理项拒绝代码生成。
· 对拍测试：用 --dump-meta 文本格式比对两个内核产生的元数据是否一致（尤其 deps 与 body-hash）。

8.11 需要先形式化验证的两条

1. 确定性展开策略（决策点 13）：把 WHNF + δ 展开顺序写成规范，用测试集验证"同一源码、不同编译顺序、不同缓存状态 → 相同转换判定"。这是整个元数据可复现性的根基。
2. 定理 body 不传播（决策点 10）：构造一个下游通过 deps 引用定理证明体的场景，验证修改该定理证明体后下游不被标记失效，但下游重编译时能正确取到新 body。这是"证明体公开但不传播"设计的边界条件，最容易实现错。

9. 构建系统与"内置数学库"体验

9.1 缓存是前提

· 内容寻址的预编译缓存作为默认行为；
· 缓存键与工具链哈希绑定；
· 用户第一次"使用内置数学库"下载增量片段，而非从源码编译。

参考量级：Mathlib 全量构建约 21 分钟（32 线程），产物约 4.5GB，云缓存约 7.3TB。仅加载策略优化就能把笔记本加载从 10.2 秒降到 2.3 秒、内存从 5.7GB 降到 1.4GB。

9.2 "内置"的真正含义

不是把 30 万声明写进内核，而是语言层内置以下机制：

1. 类型类实例合成是最大运行时瓶颈（失败搜索穷尽整个空间）。提供实例优先级/截断机制，或把合成结果缓存为声明级元数据。
2. 强制转换链深度损害编译性能（Mathlib coercion 图直径 ≥ 3，DFunLike.coe 入度约 9,519）。限制链最大长度，或做链式简并。
3. 声明级 import 绕开拉取完整闭包的问题。

9.3 声明级 import 的粒度优势

关键观察（来自 Mathlib 网络分析）：

· 约 7,563 个模块、23,570 条模块级边；
· 其下是约 308,129 个声明、840 万条声明级边；
· 人类命名空间与逻辑依赖结构约 50.9% 交叉耦合；
· 开发者平均只用到所导入作用域的 1.6%。

设计结论：声明级依赖是一等公民。每个声明在产物中携带自己的依赖元数据；下游可直接依赖单个声明，而不必拉入整个模块的公开作用域。

9.4 加载策略

· 模块索引很轻：只含 decl-id、kind、sig-hash，不含 deps 与 body。
· 声明对象按需加载：LSP 加载模块索引后，只按需读取被引用声明的 .sig，不读 .body。
· 私有作用域（若保留 private 标记）：不进入索引，不参与加载。

11. 关键决策清单

# 决策 选择 理由
1 let 内核原语 是，转换中透明展开 保留共享，规则简单
2 转换检查算法 WHNF + 惰性 delta 唯一现实选择
3 Prop 是否不可预测 是，imax 规则 兼容 Mathlib 式高阶逻辑
4 宇宙变量与累积性 内核支持层级表达式与约束，求解器在前端 支持 universe polymorphism
5 函数 η 进入 ≡ Lean 生态兼容
6 proof irrelevance 进入 ≡ 支撑"证明体修改不触发重编译"
7 三条公理形式 axiom，产生 Eq 证明，不进 ≡ 保持转换可判定与一致性
8 索引归纳族 支持 Eq、Vec、Fin 原生表达
9 严格正性 语法严格正性起步 检查简单，可后续扩展
10 大消去 Lean 式 singleton elimination 保证一致性，同时允许 Eq.rec 消去到 Type
11 ι 归约触发条件 仅 major premise 为构造子时 转换检查可判定
12 证明体可见性 公开，但不参与转换 proof irrelevance 自然挡住重编译
13 定义体默认 公开，opaque 可收紧 透明性直觉 + 可控代价
14 依赖粒度 声明级（统一 deps 集合） 模块粒度太粗（平均只用 1.6%）
15 编译单元 声明 单定理编译是通用模型实例
16 目标入口 module / modules / decl / decls 统一 语义都归约为"声明集合"
17 终止检查 前端，不入内核 内核极小化
18 商类型 语法糖 + 内核 Quot 原语 内核原语最小
19 缓存 内容寻址、默认开启 "内置库"体验的前提
20 缓存键是否含依赖哈希 否，依赖由 DepEntry 逐条判定 避免哈希级联失效
21 DepEntry 是否内嵌哈希快照 是 判定 O(依赖数)，自包含适合分布式缓存
22 确定性展开 内核转换检查必须确定性展开 元数据可复现的根基
23 DeclId 表示 限定名 + 稳定 UUID 双标识 重命名不触发重编译
24 重命名是否算签名变化 不算（可 --strict-rename） 数学库演进现实
25 序列化格式 二进制为主，文本 dump 加载性能 + 调试便利
26 定理 body 变化是否传播 完全不传播 proof irrelevance
27 expand-deps 不单独记录（路线 B 简化） 朴素闭包 + 定理例外已足够
28 inductive 变化传播 走 sig-hash 构造子是接口的一部分
29 rec 变化传播 走 body-hash 行为由 I 与 ctors 决定
30 noncomputable 变化 只重编译自身，不传播 下游由自身类型检查决定

13. 边界情况与验证重点

13.1 内核层验证

1. proof irrelevance 的实现正确性：conv 第 1 步需要准确判断"T 的 WHNF 是 Prop"，在含层级变量与 let 时需要仔细处理。
2. singleton elimination 的判定：需要静态检查归纳类型所有构造子参数类型是否都在 Prop；对索引族需处理索引参数。
3. Quot 消去子的限制：需与 Quot.sound 一致性配合，规则需形式化验证。
4. 层级约束一致性检查的完备性：内核只做一致性检查，需保证前端产生的约束不会导致内核拒绝合法项。
5. ι 归约与转换检查的终止性：标准结果成立，但索引族下需仔细验证。
6. 确定性展开：同一源码、不同编译顺序、不同缓存状态 → 相同转换判定。

13.2 元数据层验证

1. 定理 body 不传播：构造下游通过 deps 引用定理证明体的场景，验证修改该定理证明体后下游不被标记失效，但下游重编译时能正确取到新 body。
2. opaque body 不传播：类似定理。
3. def body 传播：定义体变化必须触发所有 deps 中含它的下游 dirty。
4. inductive 变化走 sig-hash：构造子列表变化触发下游 dirty。
5. rec 变化走 body-hash：I 或 ctors 变化触发 rec 变化，进而触发下游 dirty。
6. 重命名不触发重编译：stable-id 不变时，限定名变化不触发下游 dirty。
7. 缓存键不含依赖哈希：验证缓存键稳定性，不受依赖变化影响。

13.3 编译架构验证

1. 单定理编译只重建必要部分：修改一条定理，验证只有它自身与 deps 中含它的下游 dirty（且下游中 body-hash 为 Some 的才真正重编译）。
2. 模块级编译等价于批量声明编译：--module 与 --decls 全模块声明结果一致。
3. 多模块并集闭包：--modules 的闭包等于各模块闭包的并集。
4. 并行调度正确性：声明 DAG 拓扑层内并行不产生数据竞争。

13.4 工具链验证

1. LSP 增量重载：修改一条声明，LSP 只重读变化的 meta。
2. 文档生成不触碰 .body：文档生成只读 .sig + 扩展区。
3. 对拍测试：与 Lean4Lean 在基础类型检查、转换判定、元数据格式上一致。

14. 总结

14.1 设计全景

```
┌─────────────────────────────────────────────────────────────┐
│ 用户源码                                                      │
├─────────────────────────────────────────────────────────────┤
│ parser / 宏展开                                                │
│ elaborator（隐式参数、unification、类型类、coercion、终止检查）    │
├─────────────────────────────────────────────────────────────┤
│ 内核 typechecker（可信、极小）                                  │
│   - CIC 类型规则（Π、λ、应用、let、宇宙）                        │
│   - 定义性相等（β、δ、ι、η、let、proof irrelevance）             │
│   - 归纳类型（索引族、严格正性、singleton elimination）           │
│   - 层级约束一致性                                              │
│   - 三条公理作为可选常量                                        │
├─────────────────────────────────────────────────────────────┤
│ 声明级模块系统                                                  │
│   - 声明是一等原子                                              │
│   - 统一 deps 集合 + DepEntry.body-hash 存在性判定               │
├─────────────────────────────────────────────────────────────┤
│ 声明级编译驱动                                                  │
│   - 目标 → 声明集合 → 传递闭包                                  │
│   - module / modules / decl / decls 统一模型                    │
│   - is_dirty 唯一判定入口                                       │
├─────────────────────────────────────────────────────────────┤
│ 内容寻址缓存                                                    │
│   - cache-key 不含依赖哈希                                      │
│   - 默认开启，工具链哈希绑定                                      │
├─────────────────────────────────────────────────────────────┤
│ 产物：sig / body / meta + 模块索引                              │
├─────────────────────────────────────────────────────────────┤
│ 工具链：LSP / 文档 / 编译器 / 对拍 / 调试                         │
└─────────────────────────────────────────────────────────────┘
```

14.2 核心创新点

1. 声明是一等原子：编译、缓存、失效、调度统一以声明为单位，模块只是命名入口。单定理编译不是特例，而是通用模型的自然实例。
2. 朴素闭包 + 定理例外：依赖传播用最简单的朴素闭包，唯一例外是定理证明体不传播（proof irrelevance）。规则极简，元数据极简，唯一例外被编码在 DepEntry.body-hash 存在性里。
3. DepEntry.body-hash 存在性编码：体变化是否传播由被依赖对象的 kind 决定，失效判定不需要回查，只读本对象 meta。
4. 缓存键不含依赖哈希：避免哈希级联失效，失效判定逐条精确。
5. 公理可选分层：三条公理以 axiom 形式存在，产生 Eq 证明，不进入定义性相等，保持转换可判定性。
6. proof irrelevance 进入定义性相等：这是"证明体公开但不传播"的语义基础，也是路线 B 的根基。

14.3 最需前置定死的部分

1. 声明级元数据格式（第 8 节）：统一 deps 集合 + DepEntry.body-hash 存在性判定。这是整个设计中最需前期定死、后期最难改的部分。
2. 确定性展开策略（决策点 13）：保证元数据可复现性。
3. 定理 body 不传播（决策点 10）：路线 B 的唯一例外，最容易实现错。

建议在实现编译驱动前完成元数据格式设计，并用真实规模子库（如 Mathlib 的一个子集）验证失效判定正确性与性能。

14.4 一句话总结

内核极小可信；公理可选分层；声明是编译、缓存、失效、调度的统一原子；模块只是声明集合的命名入口；证明体公开但不传播失效，定义体公开且按朴素闭包传播（可 opaque 收紧）；单模块、多模块、单定理、多定理编译统一归约为"目标声明集合 + 传递闭包"。
