真实的消费者越多、写得越规范（越多用 `open` + 短名），被判成孤岛的可能越大。**

# 第 3 章 · 为什么是这个顺序

## 3.1 排序原则：**不可逆性 > 不确定性 > 杠杆率**

前两版按「杠杆率」排。第 1023 轮需要换一个更硬的判据：

| 判据 | 含义 | 为什么它优先 |
|---|---|---|
| **不可逆性** | 丢/错了能不能恢复？恢复要多久？ | 杠杆率假设「成果还在」，但这个前提本身可能不成立 |
| **不确定性** | 判断依据可不可信？ | 依据不可信则所有「后续决策」都是盲飞 |
| **杠杆率** | 解锁多少后续判定 / 成本 | 前两者合格后才启用 |

**⟹ A 层 = 「高不可逆」∪「高不确定性」。这两类的共同点是：成本固定，但失败后果被放大。**

## 3.2 为什么第一件事是「备份 + 提交」，而不是「处理孤岛」

**因为孤岛的风险是「浪费」，未提交的风险是「丢失」。**

| 风险 | 后果 | 可恢复？ |
|---|---|---|
| 7,579 行丢失 | 344 条定理消失，含 `WorldModelCapstone +298`、`FrontdoorCriterion +393` | ❌ **不可恢复**（`_r242_G*` 已丢过一次） |
| 277 个孤岛不处理 | 成果利用率低 | ✅ 可恢复（成果还在，只是没人用） |
| 指标失真不修 | 决策失误 | ✅ 可恢复（换工具即可） |

**⟹ 不可逆的风险必须先处理，即使它「不产定理」。**

**⚠ 但有一个硬约束**：入库前应过 `lake build`，而本机不可编译（9 个 require 全指向 `/root/proj/mathlib4`）。
**所以 A1 的正确做法是三步，不是「直接 `git add`」**：

```
① 仓库外冷备份（不依赖任何工具，立即执行）
② 逐文件静态核实（无 sorry / 无空壳 / 无编码损坏）
③ 分块提交，诚实标注「未经 lake build 验证」——标注，而不是假装验证过
```

## 3.3 为什么第二件事是「冻结失真指标」

**因为三个失真指标正在制造「改善」。**

`567 → 112` 这个「改善」是换口径换出来的，不是接线接出来的
（OFFSET-1023 §4.3 实测：本轮对零引用的真实改善量 **= 0**）。

**⟹ 如果不先冻结，后续任何「孤岛减少了」「消费率上升了」的报告都无法与「又换了尺子」区分。**
**这会让 A5（处理孤岛）的成果也无法验收。**

## 3.4 为什么第三件事是「换度量工具」，而不是「继续调正则」

**G46 自己写了正确的做法**：

> 「**验证法（最可靠）**：删掉 `import Fate.M` 那一行，若文件不能编译，则 M 被真消费。」

**这是编译器口径，对 Lean 是唯一正确的。** 它自动处理短名、`open`、namespace 嵌套、
类型类实例、`@[simp]` 自动应用等一切文本匹配无法处理的情形。

**而 89 轮里：「调正则」做了至少 4 次（口径 A→B→C→D），「装编译器度量」做了 0 次。**

**⟹ 这不是技术难度问题，是反馈循环问题。**
正则调起来快、立刻出数字；编译器口径要等 `lake build`（要服务器、要分钟级）。
**快而错的循环比慢而对的循环更容易被采纳——这就是它被采纳了 4 次的原因。**

**⟹ 破解方法：把「慢」变成可接受。** 全库 801 模块做编译器口径约 20+ 小时，成本过高；
但**只对 20 个样本模块做试点**，成本降到 1 天，而信息量足够判断口径是否可信。

## 3.5 为什么「把编译验证移到服务器」是 A 层而不是 D 层

**v4 把「本机不可构建」列为 D8（不做）——那是**当时**的正确判断：v4 以为原因是 Mathlib olean。**

**第 1023 轮查明真正原因有两条，第二条 v4 完全不知道**：

| 阻塞 | 内容 | v4 是否知道 |
|---|---|---|
| ① Mathlib olean | 需 8,279 个 `.olean` | ✅ 知道 |
| ② **5 个源库在本机完全不存在** | `CausSeparation` / `CausDAG` / `CausBayesBall` / `CausActivePath` / `CausBayesBallEquiv`，**99 处 import 指向它们** | ❌ **不知道** |

**⟹ ② 意味着：即使 Mathlib 装好了，本机依然不可编译。这是一个独立的、v4 未识别的阻塞。**

**为什么它是 A 层（必做）而不是 D 层（不做）：**
因为它不是「不做某件事」，而是「必须建立一条正确的验证通道」。**没有这条通道，
A1 提交的 7,579 行就永远无法被验证，S1–S3 的所有「已修」声明都只能是源码阅读。**

**⟹ 但「建立通道」的正确做法不是修 lakefile 路径**（改了只会得到「找不到库」），
而是**明确分工 + 把编译类验收全部标为「服务器执行」+ 在文档里写清本机的能力边界**。

## 3.6 为什么 D 层要明确写出「不做」

**因为第 1023 轮最大的教训是：项目有能力自己纠正，
但如果规划继续给出伪任务（如「处理 326 个扇入=0」），纠正的力气会花在错误的方向上。**

**⟹ D 层的价值 = 明确告诉执行者「这些看起来像问题，但不是」。**
