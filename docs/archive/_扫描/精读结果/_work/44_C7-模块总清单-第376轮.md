### 0.2 归类方法

**归类不按文件名字面猜测**，依据是三重证据：

1. **模块自身的文件头/描述**（每个文件首段中文说明，已逐一读取，共 565 条有效描述）；
2. **模块的实际导入表**（`^import Fate\.\w+`）；
3. **扇入数据**（`fanin_check.json` 的 `fanin_structural` / `fanin_consumption`）。

归类脚本为 `_c7_classify6.js` + `_c7_lists.js`（显式名单，可复算）。**578 个模块全部有归属，无遗漏。**

### 0.3 归类原则

1. **一个模块只归一章**（主贡献所在章）。多章相关者归「横切」。
2. **横切（ch 0）的定义**：服务于多个章的基础设施，或不属于八章正文的工程线（桥线路、N 元桥工程、装配引理、评估样例、审计记录、回归测试）。
3. **不以「定理多」为归类依据**：`Fate.Classification`（79 定理）归第 5 章而非第 1 章，因其描述为「FCA 分类系统层」。

2. **`Fate.Frame`（23 结构 / 23 消费）与 `Fate.Basic`（21 / 11）是唯一的全局基座**。二者构成「状态空间 + 四元框架」的类型层，几乎所有模块都经由它们。
3. **`Fate.WorldModel` 扇入 12/12，进入 Top 20**，但其自身只有 6 条定理。这说明「世界模型」这一类型**被引用得很广**（12 个模块依赖它），而它**承载的定理极少**——引用广泛与内容厚重不成比例，这是 C6 §1.7「交接器只有骨架」的数据印证。

### 6.4 章归属的主观性声明

**归类存在判断空间**。本文档归类可被质疑之处：

1. **「横切」占 111 个模块（19.2%）**。其中「图⟹概率」桥线路（59 个）严格说是**第 3 章的内部工程**。列为横切的依据是「大量模块互为平行竞争策略，不是主干结构」。若改归第 3 章，第 3 章将变为 244 个模块（42.2%）。
2. **`Fate.UpsilonOperator`(51) / `GammaOperator`(42) / `ComposeOperator`(21)** 归横切而非第 5 章，因四算子同时服务 α 与规则集。
3. **`Fate.Classification`（79 定理，全库第一）** 归第 5 章，因其自述为「FCA 分类系统层」。
4. **`Fate.CfPartialIdent`(48)** 归第 3 章（反事实的部分识别），但其内容与第 7 章反事实相交。
5. **`Fate.ThetaConvergence`(24)** 归第 2 章（命 = θ 的收敛），但其应用在第 7 章预测。

**凡上列判断有异议，应改的是归类而非数据**——定理数、扇入、行数不受归类影响。

### 6.5 本文档不做的判断

1. **不判断每个零扇入模块是「待接」还是「已废弃」**（见 §5.5）。
2. **不评价定理的质量或重要性**。定理数是**量**指标，不是**质**指标；`strength_check` 显示 18.4% 触发弱判据，但本清单不据此重排优先次序。
3. **不建议删除任何模块**。
4. **不修改任何 `.lean` 或既有 `.md`**。
