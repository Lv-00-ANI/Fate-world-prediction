# 发现：决定公理的是类型，不是战术

> **日期**：2026-11-02
> **发现**：专项 T17（复核 T15 的审计结论时）
> **影响**：T15 的「C 类 214 条可降级」清单**大幅失效**。

---

## 一、错误假设

T15 按「源码里有没有 simp/decide/omega」分类，判定 214 条 C 类「可降级到零公理」。

**这个前提是错的。**

## 二、决定性对照（T17 实测，我已独立复核）

| 命题 | 实测公理 |
|---|---|
| (1:ℝ)/2 + 1/2 = 1（只 
orm_num） | **三公理** |
| (c:ℝ) * 1 = c（ℝ 版 mul_one） | **三公理** |
| ∑ b : Bool, (if b = true then (1:Nat) else 0) = 1（**Nat 上**） | **三公理** |
| (⟨0,_⟩ : Fin 3) ≠ ⟨2,_⟩（只用 Fin.val） | **{}** ✅ |

**⟹ ℝ 上的算术本身就是根因；Nat 也救不了 Finset.sum。**

## 三、Predict/ 域的实测结果

108 条真 C 类（T15 说 113 条，其中 5 条其实是 D 类）：

| 通道 | 条数 |
|---|---|
| **A3 值层：引用的 def 返回 ℝ** | **89** |
| 其他（需人工） | 14 |
| A2 分数字面量（隐含 Real） | 2 |
| Finset 判定/求和 | 2 |
| Fin 实例（lt/le 走 UInt） | 1 |

**只有 2 条真能降级**（pick_addAt_any、simulate_alter_prefix，公理全来自 omega）。

**⟹ 命中率 2/108 = 1.9%。T15 的预计是 113/113。**

## 四、A3 判据必须扩展

T15 把 A3 定义为「Real 藏在**结构体字段**里」。

T17 发现必须扩展为：**同时检查「引用的 def 的返回类型」**。

`lean
-- T15 会判为「可降」，实际不可降
def condT (x z y : ℝ) : ℝ := ...
theorem some_thm : ... := ...   -- 签名里没有 ℝ，但用了 condT
`

**89 条正是栽在这里。** 只看签名 token 和结构体字段都不够，要看**整个定义的返回类型闭包**。

## 五、正确的判据

> **判据：看类型闭包，不看战术。**
>
> 类型闭包里出现 Real / Finset / Rat/Fin 的 < ⟹ 不可能零公理。
> 只有 Nat / Bool / String / 自定义 inductive ⟹ 才有降级空间。

**⟹ 在动手降级之前，先查类型闭包。若含 Real 族，别浪费时间改写法。**

## 六、对项目的影响

| 对象 | 影响 |
|---|---|
| T15 的「250 条可降级清单」 | **大幅高估**。Predict/ 域命中率仅 1.9% |
| T16 的 9/15 归零 | **仍成立**（那 15 条是纯 unext，类型干净） |
| 后续降级专项 | **必须先做类型闭包筛查**，再决定是否动手 |
| 想让全库零公理 | **必须从数据表示层去掉 Real**（即 T18 那个架构级改动） |

---

## 七、教训

> **T15 的分类器按「源码文本特征」判定可降级，而公理的真正来源是「类型」。
> 用文本特征去预测类型级属性，必然系统性高估。**

这与本项目此前的「假降级」是同一族问题的第三面：
1. 假降级：能做说成不能做
2. 假命题：追了三轮的目标本身是假的
3. **假可降：不能做说成能做**（本次）
